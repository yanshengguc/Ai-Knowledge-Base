# 项目"为什么"理解链(8/19,看了能懂,不用背)

> 用法:每节 = 为什么链(理解)→ 类比(记)→ 标准答法(说)→ 边界(加分)。
> 面试被追问"为什么",答案都在这里——理解了就能用自己的话说,不要背。

---

## ① 为什么用 RAG?(vs 直接问 LLM / 微调)

**为什么链**:
```
LLM 天生两个缺陷:知识有截止日期 + 不知道你的私有资料
→ RAG = 把知识库"喂"给模型:切片索引 → 提问时检索相关片段 → 基于资料回答
→ 知识可随时增删(重新索引),不用训练 GPU
→ 回答带引用,可验证,防幻觉
```

**类比**:开卷考试——LLM 是闭卷考生,知识库是书,检索是翻目录,回答标页码(引用),查不到就说查不到。

**标准答法**:「核心动机是私有知识 + 可更新 + 防幻觉,不是速度。相比微调:不用训练、可增删;相比直接问:不编造、省 token。」

**边界/坑**:❌ 别说"查询更快"(RAG 多一步检索,反而慢一点);✅ **Rerank 已实现**(向量+BM25 双路召回后重排),混合检索与重排都可主动讲;JD 常写 Milvus/Chroma,你用 DashVector,概念全通。

## ② 为什么用向量检索?(vs 关键词)

**为什么链**:
```
关键词 = 字面匹配 → "苹果手机续航"搜不到"iPhone 电池耐用"(没一个字相同)
向量 = Embedding 把文本变成坐标,语义相近 → 坐标近 → 找 TopK 邻居
→ 能匹配"换表达"的语义
→ 阈值(0.35)过滤太远的"邻居",防答非所问
```

**类比**:地图坐标 + 找邻居——意思相近的词坐标挨着。

**标准答法**:「关键词匹配字面,向量匹配语义,卖点是召回率不是速度。精确匹配(订单号/ID/专有名词)反而关键词更合适,所以生产常用混合检索(关键词+向量双路),这是下一步优化。」

**边界/坑**:❌ 别说"向量更快"(关键词走倒排索引也很快,向量靠 ANN 近似,不是速度优势);✅ 主动讲"混合检索"显深度。

## ③ 为什么会话记忆用 Redis?(vs 内存 Map / MySQL)

**为什么链**:
```
会话记忆 = 临时 + 高频读写 + 要过期 的数据
→ 放应用内存(Map):重启丢 + 多实例不共享(集群部署 A 机器存的,B 机器读不到)→ 崩
→ 放 MySQL:磁盘慢 + 每次序列化 + 要自己写清理过期 = 杀鸡用牛刀
→ Redis 刚刚好:内存级快 + 独立进程 + 多实例共享 + 天然 TTL 过期 + List 适合消息序列
→ 挂了降级查 MySQL,不丢对话
```

**类比**:聊天记录本——Redis List 追加,只留最近 10 条(窗口截断),带过期时间。

**标准答法**:「会话记忆是临时、高频、要过期的数据。内存不可靠(重启丢、不共享),MySQL 太重(慢、要自己清过期),Redis 卡中间:快 + 共享 + 自动过期,List 结构正好。」

**边界/坑**:❌ 别说"Redis 快所以选它"(内存比 Redis 更快——面试官会反问"那用内存?");✅ 对比三个对手才是完整答案。

## ④ 为什么上传要异步化?

**为什么链**:
```
同步处理大文件(切片+向量化)30 秒 → 三个问题:
  ① 用户干等(体验)
  ② HTTP 超时(网关/浏览器默认超时,可能断连)
  ③ Tomcat 线程被占满(默认 200 线程,一个占 30 秒 = 其他请求排队,拖垮整个应用)
→ 异步化:接口秒回"处理中",CompletableFuture 后台跑,状态机 PROCESSING→SUCCESS/FAILED,前端轮询
→ 坑:请求结束 MultipartFile 失效 → 用 ByteArrayMultipartFile(内存副本)
→ 代价:状态追踪 + 轮询 + 失败重传,但换体验和吞吐
```

**类比**:食堂点餐——下单秒回"制作中",后厨慢慢做,做好叫号(轮询);不是让顾客在窗口干站 30 秒。

**标准答法**:「同步 30 秒:用户干等 + HTTP 超时 + 线程占满拖垮别的请求。异步化 + 状态机 + 轮询解决,踩了 MultipartFile 请求后失效的坑,用 ByteArrayMultipartFile 解决。」

**边界/加分**:面试官问"为什么不用 MQ?"→「单机小规模、链路短,CompletableFuture 够用;流量大了再上 MQ 削峰解耦」——知道什么时候不需要 MQ = 架构判断力。

## ⑤ 为什么对话用 SSE?(vs 轮询 / WebSocket)

**为什么链**:
```
LLM 生成是"一个字一个字蹦"的 → 怎么让用户看到过程?
  ① 普通接口:等全部生成完一次性返回 → 用户干等 5-10 秒
  ② 轮询:每秒问"生成完没?" → 浪费请求 + 延迟 + 像"猜"状态
  ③ SSE:服务器把每个 token 直接推给浏览器 → 打字机效果 ✅
  ④ WebSocket:双向长连接 → 我只需要单向(服务器→浏览器),杀鸡用牛刀
→ SSE 基于 HTTP(不用换协议,自动重连),正好匹配"单向逐 token"
```

**类比**:水龙头——普通接口 = 烧水等开了端一整壶;轮询 = 每秒跑去问"水开了没?";SSE = 水龙头开着水滴持续流。

**标准答法**:「LLM 生成是单向逐 token 的,SSE 就是为"服务器慢慢推给浏览器"设计的:基于 HTTP、自动重连、打字机。WebSocket 双向长连接,我这场景用不上。」

**边界/坑**:❌ 别只说"流式输出"(那是效果,SSE 是实现);✅ 主动对比 WS 显深度。项目坑:SSE 末尾 usage chunk 为 null 要判空,onDone 后必须 emitter.complete()。

## ⑥ 为什么 JWT 无状态?(vs Session)

**为什么链**:
```
Session:登录状态存服务端(内存/Redis)→ 集群部署时 A 机器记的,B 机器读不到
        → 负载均衡一转,用户就掉线;发版重启也会丢
JWT:身份+过期时间编码进 token,客户端保存 → 服务端只验签
     → token 在哪台机器都能验,天然支持水平扩展,重启也不丢
代价:无法主动吊销(踢人要等过期)、只能靠 TTL、体积比 SessionID 大
```

**类比**:Session = 服务端记账本(每次查账问服务端);JWT = 盖章通行证(章真不真自己验,不用问服务端)。

**标准答法**:「Session 状态在服务端,集群不共享导致反复掉线;JWT 状态在 token 里,客户端带着走,服务端验签就行——哪台机器都能验,天然支持扩容。代价是没法主动踢人、只能等过期。」

**边界/加分**:「短生命周期 JWT 好;需要强管控(踢人/精确过期)的场景还是要服务端会话(Redis 存 Session)」——主动讲缺点 = 真懂。

## ⑦ 为什么成本治理是"记账 + 限流 + 配额"三件套?配额为什么按 token?(8/29)

**为什么链**:
```
公开演示站 = 陌生人可登录 = 你的 API key 在替别人付费
→ 只有限流(10次/分)挡不住"脚本全天匀速烧"→ 需要日预算=配额
→ 配额按 token 不按次数:一轮 Agent 对话含最多 5 次模型调用,按次会低估消耗
→ 配额数据源直接复用 token_usage 记账聚合:记账即事实源,避免 Redis 计数与 DB 双写漂移
→ 三层各挡一种攻击:记账(可见)→限流(挡突发)→配额(挡日烧)
```

**类比**:水电费——先有电表(记账),再限最大功率(限流),最后每月封顶(配额);只装电表不封顶,欠费的还是你。

**标准答法**:「成本治理是三层:token_usage 按用户/模型记账(含流式 Usage 捕获)→ 每用户限流挡突发 → 每日配额挡日烧。配额按 token 计,因为 Agent 一轮对话含多次模型调用,按次会低估;数据源直接复用记账聚合,不做第二份计数。生产配 20000 tokens/日,我自己豁免。」

**边界/坑**:❌ 别说"配额就是限流"(限流是秒级突发,配额是日级预算,维度不同);✅ 主动讲"豁免用户配置化"——多租户系统里运营者本人不限额是真实需求。

## ⑧ 为什么 Agent 模式是显式开关,而不是默认?(8/29)

**为什么链**:
```
ReAct 循环 = 模型多轮决策,一次提问可能触发多次 LLM 调用
→ 默认开 = 每个简单问题都付 5 倍延迟与成本,而多数问题根本不需要工具
→ 所以主链路保持"检索+记忆+生成"快速路径,Agent 做成显式开关(与联网开关同理:用户授权才花钱)
→ 开关打开后,模型自主决策调用工具,轨迹实时推给前端(SSE tool 事件→时间线)
```

**类比**:问路——多数时候直接告诉你(快速路径);复杂任务才派侦探出动调查(Agent),侦探按小时收费,所以要你点头。

**标准答法**:「Agent 循环有真实成本,我按'用户显式授权才花这笔钱'的原则做成开关:默认快速路径保证体验,开 Agent 换过程可见与工具能力,同时它的每次模型调用都进记账、受每日配额约束——能力开放和成本治理是配套上的。」

**边界/坑**:❌ 别说"我一开始就该把 ReAct 放进主链路"(诚实版:主链路先上线验证,Agent 按需开启是产品化时的演进判断——这是加分项不是黑历史);✅ 能讲"工具轨迹为什么执行完才推"(失败也有摘要,时间线如实展示自愈过程)。
